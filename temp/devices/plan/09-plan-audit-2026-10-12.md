## 3. What is complete

1. HCP remains the device-domain contract; LHP v1 serializes HCP across node boundaries.
2. LHP v1 request/response, batch operations, hello-first authentication, write outcome
   classification and node-side safety precheck are implemented.
3. Remote contexts enter the same `HardwareRegistry`; local and remote tool paths are
   therefore structurally identical after admission.
4. Fleet startup registration, heartbeat, degraded/offline/recovery observation and live
   plugin reload ownership transfer have board evidence.
5. R1 and J-RV2 completed without physical actuation or camera/ROS2 reconfiguration.
6. Direct TUI and daemon-stream approval gates are wired into hardware tools. A missing
   hardware gate fails closed.
7. Ordinary reads are ungated, privacy-classified reads require consent, physical writes
   require policy evaluation, and emergency stop is deliberately ungated.

## 4. What is incomplete

### 4.2 Newly explicit approval-topology gap

The current approval code works when an interactive TUI owns the direct runtime or when a
watched daemon RPC/turn owns an approval route. It does not yet provide:

- a discoverable, multi-channel `ApprovalChannel` plugin contract;
- durable pending interactions across daemon restart or client reconnection;
- an edge-headless approval inbox delivered through local web/IM/operator devices;
- authenticated approver identity and role policy across those channels;
- per-action execution permits that a remote LHP node can verify;
- exactly-once resolution when several user surfaces display the same request.

`leap hw serve` is a hardware data-plane node, not a full edge-only agent runtime. It has
no human interaction surface and must not be described as one. Today its shared LHP token
authenticates the caller and its local `SafetyPolicy` rejects unsafe declarations, but a
holder of that token can call `write` without presenting proof of a host-side human
approval. This is acceptable only inside the documented v1 trusted-control-plane boundary.
It is not sufficient for zero-trust or independently administered edge deployments.

The decision-complete target is in `10-human-approval-deployment.md`.

## 7. Jetson regression decision

No new Jetson run is necessary for this audit:

- the changes are documentation and architecture planning only;
- R1 and J-RV2 already prove the current LHP lifecycle, reload and outage/recovery paths;
- the focused local contract tests are green;
- no runtime, protocol, deployment artifact or board configuration changed.

A new board gate becomes mandatory only when Stage B–G code or Stage I approval-channel /
execution-permit code is implemented. The future gate must be read-only or simulated first;
source deployment, process start/stop, package/service/network changes and all physical
writes remain separately approval-gated.
